## Revisión del código y cambios

- `package.json` y lock: Next 16.3.4 → 16.4.5, eslint-config-next 16.2.1 → 16.4.5, Nodemailer 9.1.1 → 10.3.1. Sharp 0.35.4 → 0.35.5, Zod 4.3.6 → 4.6.7, source-map-js 1.2.1 → 1.2.2, brace-expansion 1.1.18/5.0.9 → 1.1.21/5.0.12. Se conservaron las ramas duplicadas necesarias para sus consumidores.
- Nodemailer 10 exige Node >=20; Next exige >=20.9. Se revisó el [changelog oficial](https://github.com/nodemailer/nodemailer/blob/master/CHANGELOG.md). No se usa OAuth, adjuntos, raw, DKIM ni destinos controlados por usuario. El servidor fija from/to; replyTo atraviesa el parser de direcciones. SMTP remoto sigue pendiente de validar con certificados y credenciales reales en staging.
- `app/lib/quote-request.ts`: lectura incremental de máximo 128 KiB, incluso sin Content-Length o con longitud falsa. El límite admite campos válidos máximos, UTF-8 y escapes JSON. No hay buffering ilimitado de `req.json()`. No limita por sí solo conexiones lentas: configurar tiempo y tamaño también en el proxy.
- Presupuesto de 60 solicitudes/minuto **por proceso para todo el endpoint**, antes de DB/SMTP, devuelve 429 y Retry-After. No confía en X-Forwarded-For arbitrario. Es una barrera local: no es limitación distribuida ni por usuario; se reinicia al reiniciar el proceso y un atacante puede agotar el cupo compartido. Configurar límites por cliente en el proxy confiable/WAF antes de exponer tráfico elevado.
- `app/api/send-quote/route.ts`: rechazo 403 de Origin distinto a protocolo + Host de la solicitud o Sec-Fetch-Site cross-site. Next puede construir req.url con el hostname de escucha; usar Host evita rechazar el formulario legítimo al acceder por 127.0.0.1 u otro dominio. No se admite X-Forwarded-Host como origen alternativo. Las peticiones sin Origin siguen admitidas; no es autenticación ni defensa contra bots. Verificar origen HTTPS reconstruido por el proxy en staging. No se concede CORS. Nodemailer impide lectura de archivos y URLs; no se acepta configuración de transporte desde el cliente.
- `app/lib/quote-validation.ts`: correo de una sola dirección, sin sintaxis de grupos/comentarios/display-name; nombre sin controles de cabecera. Los demás campos conservan límites y validaciones. Las consultas usan insert estructurado de Supabase, no concatenación SQL. HTML escapado; no se encontró dangerouslySetInnerHTML ni ejecución de comandos ni rutas de archivos construidas desde entradas.
- `next.config.ts`: nosniff, DENY, referrer-policy, retirada de X-Powered-By; CSP efectiva de object-src/base-uri/frame-ancestors/form-action, sin restricciones nuevas sobre scripts/estilos/workers/WASM de Spline; Cache-Control private/no-store para /api/*. Esta CSP **no es una política completa contra XSS**. HSTS pendiente de confirmar HTTPS del hosting; no se impuso includeSubDomains/preload sin comprobar subdominios.
- `app/lib/supabase.ts`: server-only, rol anon/publishable, sin session persistence ni SELECT después de INSERT. La clave pública no es un secreto; no autoriza exposición de datos privados. Verificar RLS activado y ausencia de SELECT/UPDATE/DELETE/ALL públicos. INSERT anon puede permitir abuso directo de Supabase fuera del endpoint: el presupuesto local no protege esa API externa.
- No se identificaron candidatos de secretos en el escaneo de patrones del árbol versionado actual; no hay archivos .env ni logs versionados. .gitignore excluye .env*. Esto no es un escaneo forense de todo el historial, secretos del hosting o sistemas externos.
- Paquetes sin importación directa aparente: @react-three/drei, @react-three/fiber, @react-three/postprocessing, @splinetool/react-spline y vanta (el efecto actual usa scripts de public). No se eliminaron para evitar romper consumidores indirectos. Revisar su necesidad en una limpieza independiente. Los scripts vendorizados `public/three.r134.min.js` y Vanta no quedan cubiertos por npm audit; su procedencia/actualización requiere revisión separada.

## Investigación de posible acceso no autorizado

**Clasificación: evidencia insuficiente.** No se recibieron logs HTTP, CDN, WAF, hosting, SMTP ni auditoría de Supabase. Los archivos tests/*.json y docs existentes son resultados de pruebas/documentación, no registros de accesos de terceros. No se encontró un archivo local de access logs. No hay eventos con fecha, IP, ruta, método y respuesta que permitan atribuir un intento; no se inventa una cronología. Los 403/413/429 y fallos DB/SMTP generados en esta auditoría son actividad normal de pruebas locales con datos ficticios.

No se confirma ni se descarta una intrusión histórica. La presencia de paquetes vulnerables o una solicitud a .env no probaría por sí sola acceso exitoso. No se borraron registros ni se alteró evidencia original.

Para continuar: exportar registros originales del intervalo sospechoso, zona horaria y versión desplegada; conservar copia de solo lectura y hash SHA-256. Correlacionar UTC, request-id, IP validada por proxy, método/ruta, status, bytes de respuesta, identidad y eventos DB/SMTP. Buscar traversal/.env/admin, Next-Action/RSC anómalos, URLs internas en optimización, ráfagas y errores. Una petición rechazada puede ser escaneo o intento; explotación probable requiere efectos correlacionados; compromiso confirmado requiere evidencia de acceso/ejecución/cambio no autorizado. Revisar procesos, archivos persistentes y conexiones del servidor si los logs lo justifican. Nunca registrar cuerpos de cotizaciones, contraseñas, tokens o claves en esta recopilación.

Sigue siendo un aviso real de dependencias de desarrollo.
2. Sin acceso al hosting: TLS/HSTS, comando next start, permisos del proceso, firewall, sesiones del panel administrativo, WAF, retención de logs y versión realmente publicada sin verificar. Las correcciones locales no protegen producción hasta que se revisen y desplieguen.
3. Supabase RLS, límites directos de INSERT y privacidad de cotizaciones pendientes de validación autenticada. Considerar CAPTCHA validado en servidor, control distribuido y una política de acceso restringida en un cambio de arquitectura aprobado; no introducir service_role como atajo.
4. La CSP limita capacidades de documento pero no scripts. Preparar CSP estricta en Report-Only con inventario real de Spline, blobs, WASM y Next; medir antes de imponer nonces o cambiar renderizado/caché.
5. Activar alertas de dependencias y auditoría en CI, actualizar lockfile de forma revisada, instalar con npm ci, ejecutar Node >=20.9 y publicar exclusivamente tras pruebas de staging. No se usó --force ni se habilitaron scripts de instalación bloqueados por npm.
6. El transporte conserva TLS implícito en puerto 465 y STARTTLS oportunista en otros puertos. No se verificó que el hosting ofrezca y negocie STARTTLS. Comprobarlo en staging y exigir TLS para SMTP autenticado cuando se confirme la configuración; no se desactivó la validación de certificados ni se cambió silenciosamente el protocolo del servidor.
